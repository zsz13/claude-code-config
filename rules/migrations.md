# Database migrations and schema

- Schema and data migrations are high-risk: use the `migration-review` skill
  before completion, and route review through the `adversarial-jury` at the
  high-risk tier.
- Never run a migration against anything but a local or explicitly designated
  disposable database. Never run destructive DDL (drop, truncate, type-narrowing
  alter) on shared data without the user's explicit approval of that statement.
- Every migration has a tested downgrade or a written reason it cannot have one.
  Separate expand (add nullable column, backfill, dual-write) from contract (drop
  the old path) across deploys; code and schema must be compatible in both directions
  during rollout.
- Consider locks and table size: long-running rewrites, non-concurrent index
  builds, and defaults on large tables block writes. Use the engine's online
  variants when the project's stack supports them.
- Autogenerated migrations are drafts. Read them; remove spurious diffs; name
  them for what they change.
