# Migration review

Migrations are the one change that can be correct and still take production down.
Review the migration as an *operation*, not as a diff.

## 1. Establish the facts

- Engine and version (PostgreSQL/MySQL/SQLite/other) and the migration tool
  (Alembic, Django, Prisma, Flyway, Rails, Liquibase, raw SQL).
- Which tables it touches and roughly how large they are in production. If
  unknown, say so and review for the large-table case.
- Deploy order: does the migration run before, after, or alongside the code that
  depends on it? Can old code run against the new schema and new code against
  the old one?

## 2. Checklist

**Reversibility** - a real downgrade exists and was run locally, or the file
states why it cannot exist (data destroyed). "Downgrade: pass" is a finding.

**Expand / contract** - additive first (nullable column, new table, new index),
backfill separately, switch reads, then drop the old path in a later migration.
Adding a NOT NULL column with a default, renaming, or changing a type in one
step is a finding on any non-trivial table.

**Locking** - non-concurrent index creation, table rewrites (type changes,
volatile defaults on old PostgreSQL, MySQL `ALTER` without online DDL), and
foreign-key validation on large tables block writes. Prefer `CREATE INDEX
CONCURRENTLY` (outside a transaction), `NOT VALID` + `VALIDATE`, and batched
backfills with a bounded batch size and a sleep or rate limit.

**Data loss** - dropping columns or tables, narrowing types, tightening
constraints against existing rows, truncation. Each needs the user's explicit
approval and a stated recovery path.

**Backfills** - idempotent, resumable, batched, and separate from DDL. Never a
single `UPDATE` over a large table inside the schema migration.

**Autogenerated output** - read it. Remove drift noise (server defaults, enum
churn, index renames) that is not the intended change. Name the migration for
its effect.

**Application compatibility** - ORM model, serializers, and queries agree with
the new schema; enum values and defaults match on both sides; nullable columns
are handled at read sites.

## 3. Evidence

Run the migration up, then down, then up on a local database seeded with
representative data. Capture the tool's own output and the resulting schema
diff (`alembic check`, `prisma migrate diff`, `manage.py makemigrations --check`).
For PostgreSQL, `EXPLAIN` a backfill query and note the lock type the DDL takes.

## 4. Route review

Migrations are high-risk in the `adversarial-jury`: `correctness-adversary` and
`security-judge` (if it touches auth/PII/permissions), `architecture-judge` when
the data model boundary moves. Put the up/down evidence in the packet. Strip any
real data values from it.
